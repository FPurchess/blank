# PDF tabs

Blank opens PDFs in tabs of their own, shows their pages as MuPDF draws them, and checks their signatures. It never changes a PDF in a tab (stamps, form fills and signing received PDFs come with PR 3b of the e-signing plan).

## The helper (`src-tauri/pdf`)

- **One helper process per PDF tab:** `blank-pdf` (crate `blank-pdf`, `src-tauri/pdf/helper`), shipped as a Tauri sidecar (`bundle.externalBin`) on macOS and Windows and as a resource on Linux (see Building and packaging), started by the app with `std::process` (no shell plugin). A PDF that crashes or hangs MuPDF takes down only its tab.
- **MuPDF 1.28.5** is the git submodule `src-tauri/pdf/mupdf-sys/mupdf`, pinned to Artifex's tag `1.28.5` (8ad45e92f0935d3d87f1db3f873086472a5e1b24), with its own third-party submodules. `src-tauri/pdf/mupdf-sys` is mupdf-sys 0.8.0's build glue (build.rs, make.rs, msbuild.rs, docs.rs, src/lib.rs, wrapper/), unchanged, which `[patch.crates-io]` puts in place of the crates.io crate, so it builds the submodule. Default features off, with the URW base 14 fonts. A `.ignore` there keeps cargo-about from scanning MuPDF's sources.
  - **Bumping MuPDF:** move the submodule to the new tag (`git -C src-tauri/pdf/mupdf-sys/mupdf fetch --depth 1 origin tag X && git checkout X`, then `git submodule update --init --recursive` in it), build, `bun scripts/check-mupdf-notices.ts`, `make notices`, and the tests.
  - **AGPL:** MuPDF is AGPL-3.0, like Blank. The helper's corresponding source is Artifex's tag plus our glue and shim in this repository (`src-tauri/pdf`); the FAQ says so.
- **The shim** (`helper/shim/blank_mupdf.c`) is the only code that calls MuPDF: every entry point is inside `fz_try`, so an exception is a status, never an abort. It has its own `fz_context` with a counting allocator (the memory cap: past `--memory-limit-mb`, 1536 MB, an allocation fails and the request answers `tooComplex`), a cookie to cancel a render, our font loader, and writes the form's fields and signatures as JSON (`blank_form_json`, its walk capped in fields, depth and visits). A cancel is `cancelled` even after a refused allocation; a refused allocation, MuPDF's out of memory or its limits are `tooComplex`, and so is a page whose drawing swallowed an error after a refused allocation (`cookie.errors`), rather than showing it half drawn. Rust calls it through `helper/src/mupdf.rs` only, never mupdf-sys's bindings.
- **Fonts:** a font a PDF names but doesn't embed comes from the system through `blank-system-fonts` (`src-tauri/system-fonts`, the lookup the app's `fallback_fonts` uses too): a family by name, or the CJK font of an Adobe ordering by script and language. Only fonts a PDF may embed (`embeddable`).
- **The protocol** (`src-tauri/pdf/ipc`, crate `blank-pdf-ipc`, no MuPDF, no Tauri): frames `"BPF1" | header len u32 LE | body len u64 LE | JSON header | body` (`frame.rs`) over the helper's stdin/stdout; version 1 (`protocol.rs`): the helper's first frame is a hello with `protocol` and `ops`; ops `open` (body: the PDF), `pages` (at most `PAGES_PER_REQUEST`, 4096, a request: `Supervisor::pages` batches them, since one answer for ~16k pages would outgrow the 1 MB header), `render` (answer body: RGBA, opaque, at most `MAX_PIXELS`; `serve` and the client both check the size against the pixels), `fields`, `signatures`, `cancel`, `ping`. `fields` and `signatures` (and the shim's form JSON) aren't asked by the app in this step: they are there for filling in forms and placing signature fields next, and the signature check reads the PDF itself (`signing/verify.rs`). An answer too big for a frame is sent as `tooComplex`, and `write_frame` refuses to write one. A breaking change raises `PROTOCOL` and the magic; a new op is optional within v1 (`unknownOp`); the app doesn't read the hello's `ops` yet. Positions are display points: from the top left of the crop box after `/Rotate`, UserUnit applied. `engine.rs` is the `PdfEngine`/`PdfDoc` traits MuPDF implements (a PDFium one would fit behind the same traits), `serve.rs` the helper's loop (a reader thread that takes `cancel` at once, the engine on the main thread), `client.rs` the app's side.
- **The helper's stdout carries frames only:** at start it dups fd 1 to a private fd for the frames and points fd 1 at stderr (`main.rs`). Its stderr is null in release builds (MuPDF's warnings may quote the PDF), inherited in debug builds.
- **Limits** (`client.rs`, `limits.rs`): the counting allocator first; then Linux's `RLIMIT_AS` of 4 GB (no `PR_SET_PDEATHSIG`: it fires when the *thread* that spawned the helper ends, and tokio's blocking threads retire when idle; stdin's end covers Blank going); on macOS a thread that kills a helper whose footprint passes 2.5 GB (it stops, under a lock, before the helper is reaped, so it never kills a reused PID); on Windows a job object (2.5 GB, killed with Blank) and no console window. Timeouts: start 10 s, open 20 s, render and the rest 15 s; then `cancel`, and 1 s later a kill (a hang). stdin's end makes the helper exit. A helper whose stdout closes or stops making sense is a crash; it gets 0.5 s to exit, then it's killed, so the client never waits on a live one. The client reads answers of at most `MAX_PIXELS × 4` bytes through a queue of 4. A PDF over 512 MB (`MAX_BODY`) is `tooComplex` before any helper starts. `idle_since` and `stop` never wait for a request that runs (`try_lock`): a helper in use is neither idle nor stopped. `pdf_open` puts the tab in `PdfTabs` before it opens, so a tab closed meanwhile is seen and its helper stopped.
- **Restart policy** (`Supervisor`): a crash or a hang is a failure. After the first, the next request starts a new helper, which opens the PDF again (the bytes the supervisor holds, or the file read again and checked against its SHA-256); the request that failed isn't asked again. After the second, `Failed`: the tab shows "Blank can't show this PDF any more", and **Open again** makes a new supervisor. A helper unused for 2 minutes, or past 4 running, least recently used first, is stopped, which isn't a failure.

## The app's side (`src-tauri/src/pdf_view`)

- `PdfTabs` keeps each tab's supervisor, file and SHA-256; `pdf_open` reads the file, starts the helper and returns the pages (`Opened`); `pdf_render` returns the pixels with the width and height as two u32 LE at the end (raw RGBA through `tauri::ipc::Response`, no image protocol); `pdf_cancel`, `pdf_close`; `pdf_verify` reads the file again, checks its SHA-256, and checks its signatures (below).
- Failures reach the webview as a kind (`PdfError::kind`) and the log as `PDF: <what>: <kind>`; the path of a PDF opened is logged at info. Never what a PDF holds.
- `helper_path()` finds the helper: on Linux first in `<app's dir>/../lib/blank/blank-pdf` (`/usr/lib/blank` of the packages, `usr/lib/blank` in the AppImage, `$SNAP/usr/lib/blank`; Tauri's `resource_dir` is the same folder), then next to the app (`current_exe().parent()/blank-pdf[.exe]`), where macOS's and Windows' packages have it and every build has it in `target/<profile>/` (tauri-build copies the sidecar or the resource there); in debug builds `BLANK_PDF_HELPER` may point elsewhere.

## Building and packaging

- `scripts/build-pdf-helper.ts` (`make pdf-helper`, `bun run pdf-helper`) builds the helper optimized for `TAURI_ENV_TARGET_TRIPLE` (or the host), with `MACOSX_DEPLOYMENT_TARGET=12.0`, and copies it to `src-tauri/binaries/blank-pdf-<triple>[.exe]` (git-ignored, `externalBin`'s name) and, for a Linux target, to `src-tauri/binaries/blank-pdf` too (the resource). `beforeBuildCommand`, `beforeDevCommand` and `test:rust` run it: tauri-build fails any build of the app crate without it. The first build compiles MuPDF, a few minutes; the dev profile builds mupdf-sys at opt-level 3 too. It writes a stamp next to the helper (`….stamp`, a SHA-256 of rustc, the target, MuPDF's commit and the files of `src-tauri/pdf`, `src-tauri/system-fonts`, `Cargo.toml`, `Cargo.lock` and the script) and doesn't build while the stamp matches; a MuPDF checkout with changes, or no git, always builds. `--fingerprint` prints the stamp and builds nothing; it's CI's cache key.
- **Where the packages put it:** on Linux `/usr/lib/blank/blank-pdf`, never `/usr/bin`: `src-tauri/tauri.linux.conf.json` (which Tauri merges over `tauri.conf.json` as a JSON Merge Patch for Linux builds, arrays and maps replaced whole: repeat the base's `resources` there if it ever gets any) sets `externalBin` to `[]` and maps the triple-less `binaries/blank-pdf` as a resource, which the .deb and the .rpm install in `/usr/lib/<productName>/`, the AppImage in `usr/lib/blank` of its AppDir, and the snap, which repackages the .deb, in `$SNAP/usr/lib/blank`, keeping the executable bit. Why: `/usr/bin` is for commands users run, and `blank-pdf` is an internal program only Blank starts; the FHS 3.0 puts those in `/usr/lib/<package>` (or `/usr/libexec`), Fedora's packaging guidelines in libexecdir, and Debian ships Chromium's and Firefox ESR's helpers in `/usr/lib/<package>` too. macOS keeps `externalBin` in `Contents/MacOS` (Apple's place for helper executables, and Tauri signs `externalBin` with the hardened runtime, which it doesn't do for resources); Windows keeps it next to `blank.exe`. Nothing shipped it in `/usr/bin` before, so there's nothing to migrate.
- `test-on-pr.yml` checks the packages (`usr/lib/blank/blank-pdf` in the .deb and the .rpm), the glibc floor of both binaries, that the helper runs, and its macOS minos; its macOS leg also cross-builds the helper for `x86_64-apple-darwin`, as `publish.yml` does for the Intel release, and checks it with `lipo` and `vtool`.
- **CI's cache** (`.github/actions/mupdf`, every job that needs MuPDF uses it after `actions/checkout` without submodules): it restores the submodule's git data (`.git/modules/src-tauri/pdf/mupdf-sys/mupdf`, with MuPDF's own submodules inside) keyed on the pinned commit and `.gitmodules`, then `git submodule update --init --recursive --force --depth 1`, which fetches only what the cache lacks. With `helper: true` it also restores `src-tauri/binaries/` keyed on the build script's `--fingerprint` for each target and the runner's image, so the script finds the stamp and skips the build; with `build: true` (the `pdf` job, which links MuPDF into its tests) it restores mupdf-sys's build output in `target/release` and touches it, so cargo, which checks a path dependency by mtimes, takes it as fresh. Only main saves the helper and the build output (pull requests restore main's); the git data is saved by any run that missed it. `Swatinem/rust-cache` (behind `setup-rust-toolchain`) caches neither: it drops crates inside the workspace's folder, mupdf-sys included, and every binary. Releases (`publish.yml`) restore only the sources and build the helper they ship.
- Notices: `scripts/notices/mupdf.toml` lists MuPDF, the URW fonts and the libraries of `thirdparty/` the build compiles, with their licence files in the submodule, which `build-notices.ts` quotes, and the code inside MuPDF's own sources under someone else's licence (Adobe's CMaps, UCDN, Arcfour, AES, MD5, ftoa, bidi), whose header it quotes (`header = true`); `check-mupdf-notices.ts` (the `pdf` job) fails when the build compiled a library of `thirdparty/` the list hasn't, or the other way round, and when `libmupdf.a` holds a source with a copyright other than Artifex's in its first 80 lines that isn't listed, or the CMaps (which compile into `pdf-cmap-load.o`) without them. It finds foreign code only by that header: code pasted in without one, or under Artifex's name, it can't see.
- Blank is registered as an alternate PDF viewer (`fileAssociations` role Viewer, rank Alternate; `application/pdf` in `linux/blank.desktop`), never the default.

## The webview

- **Tabs** (`src/editor/tabs.ts`, see `tabs.md`): `Tab.kind: "pdf"`. A PDF tab's `TabDocument` holds its `pdf` (`PdfTabDocument`, `src/pdf/document.ts`: the path, what opening found, the problem that shows instead of the pages, the pages that failed, the checked signatures) and an empty placeholder state (`src/pdf/placeholder.ts`), whose plugin drops every change of the document and hands the focus the editor gets on to the PDF's pages. The shown tab's PDF is `shownPdf` (`src/state/pdf.ts`); `path` and `importedFrom` are null in a PDF tab, so nothing that saves or exports markdown sees its path. Storage keeps no document of a PDF tab; it reads the PDF again when it shows, in the background (`loadTab`, `openingPdf`): the tab says "Opening …" until the helper has it, so a slow helper holds up neither the start nor a switch. `reopenPdf` is Open again and Find it…, `forgetSignatureChecks` has the signatures checked again.
- **Commands** (`src/pdf/commands.ts`): `commandFor` and the keys run every command through `forPdf`; in a PDF tab the commands of the text can't run (`editor.can` is false, so the toolbar shows them disabled) and their keys announce why (`pdfRefusal`, the one table of reasons: the main menu's disabled items and its search's results show the same sentence as their tooltip, through `MainMenuDeps.refusal`, and Export ▸ itself when every export says the same). The window's, the tabs' and the app's commands run as anywhere (`RUN_IN_PDF`: also Print, the zoom, the main menu, Keyboard shortcuts, Guide and About).
- **The view** (`src/ui/PdfView.vue`, `PdfPage.vue`, `pdfViewModel.ts`): in place of `#page-view` (`body.pdf-tab`), `#pdf-view` places the pages with `pdfDeskLayout` (`src/state/pageView.ts`: `sheetLayout` of `src/engine/frames.ts`, which the markdown pages' "pages" view uses too, at the window's zoom; Fit is one scale for the widest page, each centred), from the view's size and scroll it publishes in `pdfViewport`, mounts those near the view (`useDeskScroll`, shared with the page view, which also brings back the tab's spot and serves the page menu's `pageScrollRequest`), and asks for those without a bitmap through `RenderQueue` (`src/pdf/renderQueue.ts`: one at a time, those in view first, dropped or cancelled once they leave). A page is drawn at the next eighth above the frame's scale × the device pixel ratio, at most 16 MP (`renderScale`, `MAX_PAGE_PIXELS`, matching the helper's `MAX_PIXELS`); its bitmap's key has that scale (`pageKey`), so a zoom draws it again, and while it's drawn, the last bitmap shows stretched. Bitmaps go into `pdfBitmaps` (`src/ui/pageBitmaps.ts`), an LRU of its own (192 MB, so a third of it, the most the cache keeps of one bitmap, holds a page of `MAX_PAGE_PIXELS`: one it skipped would be drawn again and again), so a PDF never evicts the markdown pages' bitmaps; a closed tab's go (`bootApp` watches the tabs, also while no PDF shows), and a bitmap made for a tab that closed meanwhile is dropped. When the pages unmount with the focus (a markdown tab shows), the text takes it. It holds the focus (`pdfViewFocused` in `uiTakesFocus`), scrolls with the keys, and publishes `pdfPageInView` for "Page N of M". The status bar shows the page, the signatures, the paper of the first page (`pdfPaper`) and the zoom; the word count, language, spelling, view and focus mode items hide.
- **Zoom:** a PDF tab follows the window's zoom (`pageZoom`, one for every tab, as in markdown tabs; see `layout-engine.md`, "Zoom"): `sheetLayout` takes it through `sheetScale`, and `zoomFactor` reads Fit's scale from `pdfDeskLayout` in a PDF tab. It needs no engine: the zoom commands, `ZoomControl` and the main menu's Zoom row work in a PDF tab without it. A key or a button keeps the spot in the middle of the view (`middleAnchor` in `frames.ts`, which the page view's `zoomAnchorNow` uses too), Ctrl+wheel the one under the pointer (`useWheelZoom`, shared with the page view), through `zoomAnchor` and `useDeskScroll`'s `zoomed`; wider than the view, `#pdf-view` scrolls across.
- **Print:** `file.print` (Mod-P, the main menu, the tab's menu, also without the engine) prints a PDF tab's file itself, unchanged, without Blank's print dialog, whose pages, pages per sheet, scale and preview are the engine's: `printPdfFile` (`src/print/job.ts`) reads the file, checks it against the SHA-256 the tab opened (`PDF_CHANGED`, so it never prints something other than what the tab shows), and hands it to `preparePrint`/`sendPrint` on its first page's paper, one copy, actual size. Linux's dialog leaves the pages and scale chosen to Blank, which can't apply them to a foreign PDF: then it prints nothing and says `PDF_PRINTS_WHOLE`. Failures notify and announce (`insteadForPdf`: "Open the PDF in another app to print it"), a PDF Blank couldn't open says `PDF_NOT_OPEN`. E2E's `blankPrintCapture` gets the file as for Blank's documents.

## Signatures (`src-tauri/src/signing/trust.rs`, `src/ui/Signature*.vue`)

- `verify.rs` checks each signature (see `signing.md`); `Coverage` says how much of the file it covers. A timestamp token that can't be read leaves `timestamp_unreadable` set and isn't a failing check; one that doesn't hold is. `timestamp_authority` is the certificate in the token: Blank checks that the token holds, not who made it. `weak` names SHA-1 when the digest, the signature algorithm or the SubFilter relies on it. The form's fields come from `form_fields` (`signing/pdf/mod.rs`, which signing uses too): each field once (a set of the ids seen), capped in visits, depth, kids per field and the full name's length, and the pages' widgets are looked at once per page, capped too, so a hostile form can't loop or run out of memory. The check still runs in Blank's own process (lopdf reads the whole PDF there); moving it into the helper, or a process of its own, is the next step if lopdf itself turns out to be attackable.
- `trust.rs`: `classify` → `own` (the user's `certificate.cer`), `trusted` (`signing/trusted/<FINGERPRINT>.cer`, written by `signing_trust` after the user confirmed the fingerprint, removed by `signing_untrust`), `issuedBy` (not self-signed: Blank checks neither certificate authorities nor revocation), `unknown`; `status` → `valid` (whole file, or only validation data later), `signedAgainLater`, `changedAfterSigning`, `invalid`; `checked_all` makes the `CheckedSignature`s the webview shows (the time from the timestamp, else `/M`, in ISO 8601, without an offset when `/M` has none; the timestamp's authority by name, `timestampTrusted` only when its certificate is the user's or one they trust; `weak`; for `signedAgainLater`, `laterSigner`, who signed next).
- The webview: `signaturesModel.ts` says it in words: own and trusted are "Valid", the others only "Intact · says it's issued by …" (the issuer is only what the certificate claims) or "Intact · signer unknown"; the status bar's item (`SignaturesStatus.vue`, command `view.signatures`, no key) sums them up ("Not signed", "Signed", "Signed by 2", "Signed, signer unknown", "Changed and signed again", "Weak signature", "Changed after signing", "Signature invalid", and "Signatures not checked" when the check failed; nothing while it runs, and `showSignatures` then only announces it; a result that isn't "ok" is announced, quietly, once it's in). A signature signed again later is never "unchanged": it's "Valid (or Intact) for the version it signed; changed and signed again later by ‹laterSigner›"; a weak one is "Weak: SHA-1 can be forged"; a timestamp is "timestamped by ‹authority› (not checked)" unless trusted; `SignaturesPopover.vue` (request `signaturesPopover`) lists them, `SignatureDetailsDialog.vue` (request `signatureDetails`) shows one, with "Blank doesn't check certificate authorities or revocation." only in its note, and **Trust this certificate…** asks with the fingerprint (`confirmTrust`, `src/signing/trusted.ts`). Settings ▸ Signing ▸ Trusted certificates is `TrustedRows.vue`.
