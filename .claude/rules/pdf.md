# PDF tabs

Blank opens PDFs in tabs of their own, shows their pages as MuPDF draws them, and checks their signatures. It never changes a PDF in a tab: what the user fills in and places on its pages stays in Blank until they sign it, which saves a new file (see "Stamps", "Places and fills" and `signing.md`).

## The helper (`src-tauri/pdf`)

- **One helper process per PDF tab:** `blank-pdf` (crate `blank-pdf`, `src-tauri/pdf/helper`), shipped as a Tauri sidecar (`bundle.externalBin`) on macOS and Windows and as a resource on Linux (see Building and packaging), started by the app with `std::process` (no shell plugin). A PDF that crashes or hangs MuPDF takes down only its tab.
- **MuPDF 1.28.5** is the git submodule `src-tauri/pdf/mupdf-sys/mupdf`, pinned to Artifex's tag `1.28.5` (8ad45e92f0935d3d87f1db3f873086472a5e1b24), with its own third-party submodules. `src-tauri/pdf/mupdf-sys` is mupdf-sys 0.8.0's build glue (build.rs, make.rs, msbuild.rs, docs.rs, src/lib.rs, wrapper/), unchanged, which `[patch.crates-io]` puts in place of the crates.io crate, so it builds the submodule. Default features off, with the URW base 14 fonts. A `.ignore` there keeps cargo-about from scanning MuPDF's sources.
  - **Bumping MuPDF:** move the submodule to the new tag (`git -C src-tauri/pdf/mupdf-sys/mupdf fetch --depth 1 origin tag X && git checkout X`, then `git submodule update --init --recursive` in it), build, `bun scripts/check-mupdf-notices.ts`, `make notices`, and the tests.
  - **AGPL:** MuPDF is AGPL-3.0, like Blank. The helper's corresponding source is Artifex's tag plus our glue and shim in this repository (`src-tauri/pdf`); the FAQ says so.
- **The shim** (`helper/shim/blank_mupdf.c`) is the only code that calls MuPDF: every entry point is inside `fz_try`, so an exception is a status, never an abort. It has its own `fz_context` with a counting allocator (the memory cap: past `--memory-limit-mb`, 1536 MB, an allocation fails and the request answers `tooComplex`), a cookie to cancel a render, our font loader, and writes the form's fields and signatures as JSON (`blank_form_json`, its walk capped in fields, depth and visits). A cancel is `cancelled` even after a refused allocation; a refused allocation, MuPDF's out of memory or its limits are `tooComplex`, and so is a page whose drawing swallowed an error after a refused allocation (`cookie.errors`), rather than showing it half drawn. Rust calls it through `helper/src/mupdf.rs` only, never mupdf-sys's bindings.
- **Fonts:** a font a PDF names but doesn't embed comes from the system through `blank-system-fonts` (`src-tauri/system-fonts`, the lookup the app's `fallback_fonts` uses too): a family by name, or the CJK font of an Adobe ordering by script and language. Only fonts a PDF may embed (`embeddable`).
- **The protocol** (`src-tauri/pdf/ipc`, crate `blank-pdf-ipc`, no MuPDF, no Tauri): frames `"BPF1" | header len u32 LE | body len u64 LE | JSON header | body` (`frame.rs`) over the helper's stdin/stdout; version 1 (`protocol.rs`): the helper's first frame is a hello with `protocol` and `ops`; ops `open` (body: the PDF), `pages` (at most `PAGES_PER_REQUEST`, 4096, a request: `Supervisor::pages` batches them, since one answer for ~16k pages would outgrow the 1 MB header), `render` (answer body: RGBA, opaque, at most `MAX_PIXELS`; `serve` and the client both check the size against the pixels), `text` (`PageText`: the words of the page's contents and annotations, not the widgets' values, each box spanning at most 0.8 em above the baseline and 0.25 below, as MuPDF's quads span the font's line gap too; and `rules`, drawn thin horizontals ≥ 40 pt wide, ≤ 2 pt high, not white), `fields` (a choice's `options` and `value` by their display texts, of `[export display]` pairs too; the signature check reads the PDF itself, `signing/verify.rs`, so there's no op for signatures), `setFills` (stateless: the whole set, on a document opened afresh from the bytes, appearances regenerated by MuPDF with `pdf_update_page` on the pages loaded together; answers the pages whose fields' values changed; a refused set keeps the last, and its failure names the field of the fill that failed, `Failure::field`), `save` (an incremental update of the filled document, from a document opened afresh, since MuPDF counts what it wrote as saved; refused `repaired`, also for bytes before the header, whose offsets `pdf_write_document` gets wrong, and `encrypted`), `cancel`, `ping`. **Fills** (`Fill`): a checkbox `true`/`false`, a radio group the `onValue` of a widget or "Off", a choice one of its options by what it shows (its export value is set) or any text in an editable combo box, a text field its text (within `/MaxLen`, one line unless multiline; a tab is a space, `filled` in mupdf.rs). MuPDF draws every field's value in the base 14 font its `/DA` names (else Helvetica) with Windows-1252, and anything else in fonts it doesn't embed or as a replacement character, so a value with characters outside that encoding or font is refused `missingGlyphs` (`shows` in the shim), never set. It's checked on what MuPDF draws: a text field's value, a combo box's export value (MuPDF draws `/V`, not the display text), every option of a list box (it draws them all). `choices.pdf` has such pairs. Read-only, push button and signature fields, unknown names and a name that only starts a field's are `badRequest`. The supervisor keeps the fills that held (`Supervisor::set_fills`, `fills`; a refusal is `Refused { error, field }`) and gives a new helper them again after `open`; `save`'s answer may be as big as the PDF and a page's pixels (`max_answer`). An answer too big for a frame is sent as `tooComplex`, and `write_frame` refuses to write one. A breaking change raises `PROTOCOL` and the magic; a new op is optional within v1: the client asks no op the hello's `ops` lacks (`unknownOp`), and an engine without one answers `unknownOp` (the traits' defaults). Positions are display points: from the top left of the crop box after `/Rotate`, UserUnit applied. `engine.rs` is the `PdfEngine`/`PdfDoc` traits MuPDF implements (a PDFium one would fit behind the same traits), `serve.rs` the helper's loop (a reader thread that takes `cancel` at once, the engine on the main thread), `client.rs` the app's side.
- **The helper's stdout carries frames only:** at start it dups fd 1 to a private fd for the frames and points fd 1 at stderr (`main.rs`). Its stderr is null in release builds (MuPDF's warnings may quote the PDF), inherited in debug builds.
- **Limits** (`client.rs`, `limits.rs`): the counting allocator first; then Linux's `RLIMIT_AS` of 4 GB (no `PR_SET_PDEATHSIG`: it fires when the *thread* that spawned the helper ends, and tokio's blocking threads retire when idle; stdin's end covers Blank going); on macOS a thread that kills a helper whose footprint passes 2.5 GB (it stops, under a lock, before the helper is reaped, so it never kills a reused PID); on Windows a job object (2.5 GB, killed with Blank) and no console window. Timeouts: start 10 s, open 20 s, `setFills` 10 s, `save` 30 s, render and the rest 15 s; then `cancel`, and 1 s later a kill (a hang). stdin's end makes the helper exit. A helper whose stdout closes or stops making sense is a crash; it gets 0.5 s to exit, then it's killed, so the client never waits on a live one. The client reads answers of at most `MAX_PIXELS × 4` bytes, `save`'s of the PDF opened and that much more, through a queue of 4: each answer is held to its own request's limit (`AnswerLimit`, the request's id and limit, set before it's written), which the reader picks once it read the answer's header (`read_frame_by`), so an answer never gets the limit of the request before or after it. A PDF over 512 MB (`MAX_BODY`) is `tooComplex` before any helper starts. `idle_since` and `stop` never wait for a request that runs (`try_lock`): a helper in use is neither idle nor stopped. `pdf_open` puts the tab in `PdfTabs` before it opens, so a tab closed meanwhile is seen and its helper stopped.
- **Restart policy** (`Supervisor`): a crash or a hang is a failure. After the first, the next request starts a new helper, which opens the PDF again (the bytes the supervisor holds, or the file read again and checked against its SHA-256); the request that failed isn't asked again. After the second, `Failed`: the tab shows "Blank can't show this PDF any more", and **Open again** makes a new supervisor. A helper unused for 2 minutes, or past 4 running, least recently used first, is stopped, which isn't a failure.

## The app's side (`src-tauri/src/pdf_view`)

- `PdfTabs` keeps each tab's supervisor, file and SHA-256; `pdf_open` reads the file, starts the helper and returns the pages (`Opened`); `pdf_text`, `pdf_fields` and `pdf_set_fills` (src/pdf/ipc.ts: `pageText`, `pdfFields`, `setFills`, types `PageText`, `PdfField`, `Fill`) ask the tab's helper (`pdf_set_fills` fails with `{ kind, field }`: the kind, as the others fail with, and the full name of the field whose fill the helper refused, else null; the name never reaches the log); `filled_bytes` gives the signer the file (read again and checked against its SHA-256: `FileChanged`/`FileMissing`) as it is without fills, else with them as MuPDF's incremental update, which must start with the file's bytes; words and values never reach the log; `pdf_render` returns the pixels with the width and height as two u32 LE at the end (raw RGBA through `tauri::ipc::Response`, no image protocol); `pdf_cancel`, `pdf_close`; `pdf_verify` reads the file again, checks its SHA-256, and checks its signatures (below); `pdf_print` reads it again (`read_checked`) and hands it to the system's print dialog through `print::prepare`/`print::send`, so a PDF of up to 512 MB never travels through the webview.
- Failures reach the webview as a kind (`PdfError::kind`) and the log as `PDF: <what>: <kind>`; the path of a PDF is logged at info when it opens (`PDF: opening <path>`), never in a warning. Never what a PDF holds. A file read again that isn't the one opened is told apart: `missing` (it went), `changed` (it holds another PDF), `unreadable`: `pdf_render` turns `PdfError::Source` (a helper stopped while idle that can't open it again) into one of them (`file_problem`), `pdf_print` fails with the `PrintError` kinds `missing`/`changed`/`notOpen`, and `pdf_verify` says it in its message.
- `helper_path()` finds the helper: on Linux first in `<app's dir>/../lib/blank/blank-pdf` (`/usr/lib/blank` of the packages, `usr/lib/blank` in the AppImage, `$SNAP/usr/lib/blank`; Tauri's `resource_dir` is the same folder), then next to the app (`current_exe().parent()/blank-pdf[.exe]`), where macOS's and Windows' packages have it and every build has it in `target/<profile>/` (tauri-build copies the sidecar or the resource there); in debug builds `BLANK_PDF_HELPER` may point elsewhere.

## Building and packaging

- `scripts/build-pdf-helper.ts` (`make pdf-helper`, `bun run pdf-helper`) builds the helper optimized for `TAURI_ENV_TARGET_TRIPLE` (or the host), with `MACOSX_DEPLOYMENT_TARGET=12.0`, and copies it to `src-tauri/binaries/blank-pdf-<triple>[.exe]` (git-ignored, `externalBin`'s name) and, for a Linux target, to `src-tauri/binaries/blank-pdf` too (the resource). `beforeBuildCommand`, `beforeDevCommand` and `test:rust` run it: tauri-build fails any build of the app crate without it. The first build compiles MuPDF, a few minutes; the dev profile builds mupdf-sys at opt-level 3 too. It writes a stamp next to the helper (`….stamp`, a SHA-256 of rustc, the C compiler's and clang's versions, the target, MuPDF's commit, the files of `src-tauri/pdf` and `src-tauri/system-fonts` without their tests and fixtures, the script, the crates the helper is built from as `cargo tree -p blank-pdf -e normal,build --target <triple>` resolves them, the workspace's `[profile.release]` and `[patch]`, the Cargo configuration files and the environment the build takes compilers and flags from: `CC`/`CC_<triple>`/`TARGET_CC`, `CFLAGS_*`, `AR`, `RUSTFLAGS`, `CARGO_ENCODED_RUSTFLAGS`, `CARGO_TARGET_<T>_RUSTFLAGS`/`LINKER`, `CARGO_PROFILE_RELEASE_*`, …) and doesn't build while the stamp matches, so a dependency of the app alone doesn't rebuild MuPDF; a MuPDF checkout with changes (its submodules included), or no git, always builds. It runs cargo in `src-tauri`, so the configuration it reads is the one hashed. `--fingerprint` prints the stamp and builds nothing; it's CI's cache key.
- **Where the packages put it:** on Linux `/usr/lib/blank/blank-pdf`, never `/usr/bin`: `src-tauri/tauri.linux.conf.json` (which Tauri merges over `tauri.conf.json` as a JSON Merge Patch for Linux builds, arrays and maps replaced whole: repeat the base's `resources` there if it ever gets any) sets `externalBin` to `[]` and maps the triple-less `binaries/blank-pdf` as a resource, which the .deb and the .rpm install in `/usr/lib/<productName>/`, the AppImage in `usr/lib/blank` of its AppDir, and the snap, which repackages the .deb, in `$SNAP/usr/lib/blank`, keeping the executable bit. Why: `/usr/bin` is for commands users run, and `blank-pdf` is an internal program only Blank starts; the FHS 3.0 puts those in `/usr/lib/<package>` (or `/usr/libexec`), Fedora's packaging guidelines in libexecdir, and Debian ships Chromium's and Firefox ESR's helpers in `/usr/lib/<package>` too. macOS keeps `externalBin` in `Contents/MacOS` (Apple's place for helper executables, and Tauri signs `externalBin` with the hardened runtime, which it doesn't do for resources); Windows keeps it next to `blank.exe`. Nothing shipped it in `/usr/bin` before, so there's nothing to migrate.
- **MuPDF's FreeType stays inside the helper:** MuPDF compiles its own FreeType in. Had the helper linked libfontconfig, the executable would export it and fontconfig would call it in place of the system's (a mix of both versions, and font caches written with MuPDF's slim FreeType into `~/.cache/fontconfig`). So `blank-system-fonts` takes fontique with `fontconfig-dlopen`: fontconfig is loaded at run time (`libfontconfig.so.1`; without it the helper finds no system fonts), the helper exports no symbol, and building it needs no fontconfig or FreeType headers.
- `test-on-pr.yml` checks the packages (`usr/lib/blank/blank-pdf` in the .deb and the .rpm), the glibc floor of both binaries, that the helper runs, its macOS minos, and that the Linux helper exports no `FT_*` and doesn't link libfontconfig; its macOS leg also cross-builds the helper for `x86_64-apple-darwin`, as `publish.yml` does for the Intel release, and checks it with `lipo` and `vtool`.
- **CI's cache** (`.github/actions/mupdf`, every job that needs MuPDF uses it after `actions/checkout` without submodules): it restores the submodule's git data (`.git/modules/src-tauri/pdf/mupdf-sys/mupdf`, with MuPDF's own submodules inside) keyed on the pinned commit and `.gitmodules`, then `git submodule update --init --recursive --force --depth 1`, which fetches only what the cache lacks. With `helper: true` it also restores `src-tauri/binaries/` keyed on the build script's `--fingerprint` for each target and the runner's image, so the script finds the stamp and skips the build; with `build: true` (the `pdf` job, which links MuPDF into its tests) it restores mupdf-sys's build output in `target/release` and touches it, so cargo, which checks a path dependency by mtimes, takes it as fresh. Only main saves the helper and the build output (pull requests restore main's); the git data is saved by any run that missed it. `Swatinem/rust-cache` (behind `setup-rust-toolchain`) caches neither: it drops crates inside the workspace's folder, mupdf-sys included, and every binary. Releases (`publish.yml`) restore only the sources and build the helper they ship.
- Notices: `scripts/notices/mupdf.toml` lists MuPDF, the URW fonts and the libraries of `thirdparty/` the build compiles, with their licence files in the submodule, which `build-notices.ts` quotes, and the code inside MuPDF's own sources under someone else's licence (Adobe's CMaps, UCDN, Arcfour, AES, MD5, ftoa, bidi), whose header it quotes (`header = true`); `check-mupdf-notices.ts` (the `pdf` job) fails when the build compiled a library of `thirdparty/` the list hasn't, or the other way round, and when `libmupdf.a` holds a source with a copyright other than Artifex's in its first 80 lines that isn't listed, or the CMaps (which compile into `pdf-cmap-load.o`) without them. It finds foreign code only by that header: code pasted in without one, or under Artifex's name, it can't see.
- Blank is registered as an alternate PDF viewer (`fileAssociations` role Viewer, rank Alternate; `application/pdf` in `linux/blank.desktop`), never the default.

## The webview

- **Tabs** (`src/editor/tabs.ts`, see `tabs.md`): `Tab.kind: "pdf"`. A PDF tab's `TabDocument` holds its `pdf` (`PdfTabDocument`, `src/pdf/document.ts`: the path, what opening found, the problem that shows instead of the pages, the pages that failed, the checked signatures) and an empty placeholder state (`src/pdf/placeholder.ts`), whose plugin drops every change of the document and hands the focus the editor gets on to the PDF's pages. The shown tab's PDF is `shownPdf` (`src/state/pdf.ts`); `path` and `importedFrom` are null in a PDF tab, so nothing that saves or exports markdown sees its path. Storage keeps no document of a PDF tab; it reads the PDF again when it shows, in the background (`openingPdfTab`, `openInBackground`, for a restored tab in `loadTab` and for one opened from the command line, the file manager or Open in `pdfTab`): the tab says "Opening …" until the helper has it, so a slow helper holds up neither the start, nor a switch, nor the tabs' queue, and a PDF it can't open says why in its tab. The result lands only while the tab still shows that opening (by identity), so Open again meanwhile wins. `reopenPdf` is Open again and Find it… (it shows "Opening …" too; then the pages take the focus back), `showPdfProblem` puts a tab's problem in place of its pages (printing found the file gone or changed), and `forgetSignatureChecks` has the signatures checked again, counting in `signatureChecks`, so a check in flight when trust changed is done again (`PdfView.vue`). The problems (`PdfProblem`, `problemText`): missing (Find it…), unreadable, changed, damaged (also a PDF without pages), tooComplex (also a timeout or hang), needsPassword, start, stopped (a crash while it opened), failed (two crashes); a render's failure goes through `withRenderFailure`: the tab's problem for `failed`/`missing`/`changed`/`unreadable`/`start`, else "couldn't draw" on that page. A `closed` failure (the tab closed or opened again) isn't logged.
- **Commands** (`src/pdf/commands.ts`): `commandFor` and the keys run every command through `forPdf`; in a PDF tab the commands of the text can't run (`editor.can` is false, so the toolbar shows them disabled, the style menu and Insert ▸ Table included (`formatToolbarModel.ts`), and the tab row's Blocks button with `pdfRefusal` as its tooltip) and their keys announce why (`pdfRefusal`, the one table of reasons, each a sentence: the main menu's disabled items and its search's results show the same sentence as their tooltip, through `MainMenuDeps.refusal`, and Export ▸ itself, with the first export's reason, when every export refuses). Every way to sign your own documents (Export signed PDF, Signature block, Your signature…, Your initials…) says `SIGN_RECEIVED_REFUSAL` ("In a PDF, place your signature from the signing toolbar, then choose Sign on it. …"). Save and Save as say `SIGN_TO_KEEP`, but Save's key runs `pdf.sign`; Undo and Redo run the stamps' history while it has a step, else say there's nothing to undo or redo. The window's, the tabs' and the app's commands run as anywhere (`RUN_IN_PDF`: also Print, the zoom, the main menu, Keyboard shortcuts, Guide and About).
- **The view** (`src/ui/PdfView.vue`, `PdfPage.vue`, `pdfViewModel.ts`): in place of `#page-view`, `#pdf-view` places the pages with `pdfDeskLayout` (`src/state/pageView.ts`: `sheetLayout` of `src/engine/frames.ts`, which the markdown pages' "pages" view uses too, at the window's zoom; Fit is one scale for the widest page, each centred), from the view's size and scroll it publishes in `pdfViewport`, mounts those near the view (`useDeskScroll`, shared with the page view, which also brings back the tab's spot and serves the page menu's `pageScrollRequest`), and asks for those without a bitmap through `RenderQueue` (`src/pdf/renderQueue.ts`: one at a time, those in view first, dropped or cancelled once they leave). A page is drawn at the next eighth above the frame's scale × the device pixel ratio, at most 16 MP (`renderScale`, `MAX_PAGE_PIXELS`, matching the helper's `MAX_PIXELS`); its bitmap's key has that scale (`pageKey`), so a zoom draws it again, and while it's drawn, the last bitmap shows stretched. Bitmaps go into `pdfBitmaps` (`src/ui/pageBitmaps.ts`), an LRU of its own (192 MB, so a third of it, the most the cache keeps of one bitmap, holds a page of `MAX_PAGE_PIXELS`: one it skipped would be drawn again and again), so a PDF never evicts the markdown pages' bitmaps; the pages mounted are pinned there (`pin`), so at a large zoom they go over its room for a while rather than drawing each other away forever; `RenderQueue` draws a page again that was cancelled and wanted back before the cancel came back; a closed tab's go (`bootApp` watches the tabs, also while no PDF shows), and a bitmap made for a tab that closed meanwhile is dropped. When the pages unmount with the focus (a markdown tab shows), the text takes it. It holds the focus (`pdfViewFocused` in `uiTakesFocus`), scrolls with the keys (Tab and Shift-Tab move the focus as anywhere, not Indent's refusal), and publishes `pdfPageInView` for "Page N of M". The status bar shows the page, the signatures, the paper of the first page (`pdfPaper`) and the zoom; the word count, language, spelling, view and focus mode items hide.
- **Zoom:** a PDF tab follows the window's zoom (`pageZoom`, one for every tab, as in markdown tabs; see `layout-engine.md`, "Zoom"): `sheetLayout` takes it through `sheetScale`, and `zoomFactor` reads Fit's scale from `pdfDeskLayout` in a PDF tab. It needs no engine: the zoom commands, `ZoomControl` and the main menu's Zoom row work in a PDF tab without it. A key or a button keeps the spot in the middle of the view (`middleAnchor` in `frames.ts`, which the page view's `zoomAnchorNow` uses too), Ctrl+wheel the one under the pointer (`useWheelZoom`, shared with the page view), through `zoomAnchor` and `useDeskScroll`'s `zoomed`; wider than the view, `#pdf-view` scrolls across.
- **Print:** `file.print` (Mod-P, the main menu, the tab's menu, also without the engine) prints a PDF tab's file itself, unchanged, without Blank's print dialog, whose pages, pages per sheet, scale and preview are the engine's: `printPdfFile` (`src/print/job.ts`) has the native side print it (`printPdfTab`, `pdf_print`), which reads the file, checks it against the SHA-256 the tab opened (so it never prints something other than what the tab shows), and hands it to the system's dialog on its first page's paper, one copy, actual size. A file that changed or went says `PDF_CHANGED`/`PDF_MISSING`, and its tab then shows the problem with Open again or Find it… (`showPdfProblem`). Linux's dialog leaves the pages and scale chosen to Blank, which can't apply them to a foreign PDF: Blank says so before the dialog opens (`PDF_PRINTS_WHOLE_FIRST`), and if they're chosen all the same it prints nothing and says `PDF_PRINTS_WHOLE` (outcome `whole`). Failures notify and announce (`insteadForPdf`: "Open the PDF in another app to print it"), a PDF Blank couldn't open says `PDF_NOT_OPEN`, one still opening `PDF_STILL_OPENING`. E2E's `blankPrintCapture` gets the file as for Blank's documents.

## Stamps (`src/pdf/stamp*.ts`, `src/ui/Stamp*.vue`, `src/ui/SigningToolbar.vue`)

- **The model** (`src/pdf/stampModel.ts`, pure): a `Stamp` is `{ id, kind: signature | initials | date | place, page (from 0), rect (display points), natural (its size when placed), repeat? (initials only), place? (the found place it fills), spec (its `StampSpec` at the natural size; `scaledSpec` scales the letters with the rect) }`. `clampRect` keeps ≥ `MIN_ON_PAGE` (10 pt) on the page, `nudge`/`moveTo`, `resizeTo`/`resizeBy` (shape kept, 50–300 % of `natural`, from the fixed corner), `withStamp`/`withoutStamp`/`toggleRepeat`, `ghostsOf` (repeated initials on the other pages, `fitInto` them as `stamp.rs`'s `repeat_into` does: made smaller, shape kept, where they don't fit, and as far from the nearer of the left and right edges and of the top and bottom edges as on the page they were placed on, a tie going left and up, never off the page), `defaultSpot` (a signature centred in the lower third of what shows of the page in view, initials in the bottom right corner as a signed export puts them, `initialsRect` of `src/signing/initials.ts`, a date or place `GAP` below the last signature and what stands under it, else as a signature) and `spotAt` (centred on a click). Signature and initials are `markSize` (the picture's shape in 180 × 60 or 56 × 28 pt), dates and places their `naturalSize` from the stamp engine. The history is a `StampBook` of snapshots (`Sheet`: the stamps, the form's `fills` and the `dismissed` found places, so one undo steps back through whichever changed; `changedSheet`/`changed`, `undone`, `redone`, 100 deep; nudges of one stamp within 500 ms are one step; a drag is one step, since it commits once on release).
- **State** (`src/state/stamps.ts`): `stampBooks` (each PDF tab's `{ book, sha256 }` by tab id), `selectedStamp`, `placingStamp` (the tool a click armed), `shownPdfRules`, `signingTabs` (the tabs being signed, whose stamps, fills and places wait: `changeStamps`, `changeSheet`, undo and redo say `SIGNING` and change nothing), and for the places `pdfPlaces`, `pageRevisions`, `fieldProblem`, `lastPlace` (below). Written only through `src/pdf/stampBooks.ts` (`changeStamps`, `undoStamps`/`redoStamps`, `forgetStamps` when the tab closes, `restoreStamps`), which frees the engines of looks no stamp has any more (`releaseStamp`; `isHeld` tells whether one is kept, so the export frees its initials' engine unless a tab holds that look); `src/pdf/stampActions.ts` is what the tools and keys do (`placeStamp`: makes the signature first through `openSignatureDialog` when there's none, places, selects, announces "Signature placed on page 2, use the arrow keys to move it"; `removeStamp` "Signature removed", returning the stamp, and `focusFreed` gives the place it filled the focus once it shows again, else the pages, from Delete on it and Remove on its toolbar alike, `repeatStamp`, `updateStamp` (a stamp moved or resized off the place it filled, its middle outside it, `staysOn`, leaves it, so the place shows again), `cancelPlacing` "Placing canceled"). The date is `todayText` (`src/editor/commands/signing.ts`: the settings' format, in the language), the place `signingPlace`; without one, a place stamp first asks for it (`askPlace`: `PlaceDialog.vue`, request `placeDialog`, "Where do you sign?", remembered in `signingPlace`), from the Place tool and from a found place alike.
- **Unsaved and storage:** a PDF tab with stamps or fills is unsaved (`hasChanges`, `refresh` in `src/editor/tabs.ts`, which follows `stampBooks`). Storage writes `stamps:<id>` = `{ sha256, stamps, fills, dismissed }` with the documents' debounce and removes it when none are left or the tab closes; `loadStamps` reads it (`isStamp` and `isFill` drop what they can't read). Every open of a tab's PDF runs `restoreStamps` (`openInBackground`, also for Open again and Find it…): the first time it brings back what was stored, unless something was placed meanwhile; then what the tab holds is made to fit the file opened (`fitted`): the same SHA-256 as it was, a changed file without the stamps on pages it no longer has and without fills, dismissed places and history (announced when stamps or fills went), a file gone or not open as it was. Closing a PDF tab with stamps asks through `UnsavedDialog` ("Sign “‹name›” before you close it?", Discard · Cancel · Sign…, its `title`/`text`/`saveLabel`/`discardLabel`); Sign… runs `signReceived` and keeps the tab.
- **What may be placed** (`src/pdf/toolRules.ts`, pure, on a `ToolContext`: the PDF opened, its rules, whether the engine runs, whether it's being signed, how many signature stamps it has; `shownContext` in `placesRead.ts` makes the shown tab's): `signing_pdf_rules(path, sha256)` (`signing/commands.rs`, `rules.rs`; `fileChanged`/`fileMissing` when the file isn't the one the tab opened) gives `{ signed, docmdp, encrypted, damaged, locked }`, read once per file the tab shows (`readShownRules`, `src/pdf/sign.ts`, into `shownPdfRules`; a failure reads as no limits, and the signer refuses natively). `blocked` (not open, encrypted, repaired/damaged, P=1: nothing, with the toolbar's note), `toolRefusal` (being signed: `SIGNING`; no engine: `STAMPS_NEED_LAYOUT`, the one sentence for it, in `stamps.ts`; signed or certified: initials, date and place off, each naming itself, and a second signature stamp, `ONE_SIGNATURE`, since only one becomes the signature's appearance), `fieldRefusal` (being signed, rules not read yet, a field an earlier signature locked: `FIELD_LOCKED`), `placeRefusal` (a place as its stamp's tool, else as its field), `signRefusal`, `visibleRefusal` (signed or certified: no signature without a certificate, which would go into the pages' content). `RESTRICTED` and `NO_CHANGES` are the native `Refusal`'s words, which `toolRules.test.ts` compares with `mod.rs`.
- **Signing toolbar** (`SigningToolbar.vue`, `signingToolbarModel.ts`): in place of the formatting toolbar in a PDF tab (`TopArea.vue`), the same F6 stop and Alt-F10 (`useFocusRegion` "toolbar", `useRovingFocus`): Signature · Initials · Date · Place, Sign… (`pdf.sign`, no default key; Save's key runs it in a PDF tab through `forPdf`), Next (below; hidden while the PDF has no places), and a note when no tool works. A tool from the keyboard (a click with `detail` 0) places at the default spot and gives the new stamp the focus; a click arms it (`placingStamp`, `aria-pressed`, the crosshair `#pdf-view.pdf-placing`) and a press on a page (`onDeskPress` in `PdfView.vue`) places it there; Esc or a second click puts it down. A disabled tool is `aria-disabled` with its reason as its tooltip, and a press announces it. `pdf.sign` signs (`signReceived`, see `signing.md`, "Stamps and signing received PDFs").
- **On the pages** (`StampOverlay.vue`, `stampOverlayModel.ts`, `stampDrag.ts`, `StampToolbar.vue`): `PdfView.vue` puts every stamp of the tab (not only of mounted pages), with the places (below), in `.page-desk` after the pages, in reading order (`readingOrder` of `places.ts`: page, line band, x), so Tab follows it (the sheets and `PdfPage` are `aria-hidden`, the desk isn't); each is `role="group"` labelled `stampLabel` ("Signature on page 2, selected"), `tabindex` 0, `#stamp-<id>`, at `stampBox` (display points × the layout's scale on its page's frame), painted by `paintStamp` at that scale (again on `imagesLoaded`). Focus selects it: the accent ring (`outline-offset: 3px`), four `.stamp-handle` corners, and `StampToolbar` right after it in the DOM (Remove; for initials "Repeat on every page", `aria-pressed`), above it, or below at the top. Keys (`stampKeyAction`): arrows nudge 1 pt (Shift 10), Alt+arrows resize, Delete/Backspace remove (the pages take the focus), Esc deselects; the rest goes on to the page view, whose `commandKeys` run Undo/Redo through `forPdf` on the stamps' history. The mouse: pointer capture, `DRAG_START` 4 px, move or resize from a corner (the opposite one fixed), a preview until release. Ghosts of repeated initials are `aria-hidden`, at 0.6 opacity, without pointer events, on the pages mounted only. A stamp that unmounts with the focus gives it to the pages.

## Places and fills (`src/pdf/places.ts`, `placeModel.ts`, `placesRead.ts`, `placeActions.ts`, `fills.ts`, `PdfTarget.vue`, `PdfField.vue`)

- **Reading them** (`readPlaces`, from `PdfView.vue` once a PDF shows): `pdfFields(tab)` first, then `pageText` → `findLabels` (`src/signing/labels.ts`) page by page, publishing after each into `pdfPlaces` (by tab, for the SHA-256 read; once per opened PDF; dropped when the tab closes, `forgetPlaces` in `mount.ts`). Failures are logged by kind only, never words or values. `shownPlaces` (a computed) is `placesOf` of the shown tab with `shownPdfRules`' `locked` (such a field is a place with `locked`, shown disabled, never open: `isOpen`, so Next, the Sign dialog's count and Next's count pass it) and the book's `dismissed`; `shownStamps` the stamps on the pages the PDF has; `shownFilled` (`filledOf`: a stamp with `place` = its id, or a field holding a value) and `shownNext` (`nextButton` from `lastPlace`, the place focused last, which a tab switch resets in `bootApp`). Place ids are `fieldPlaceId(name)` and `found:<page>:<x>:<y>`; `fieldOfPlace` reads a field's name back. Places, stamps and the overlays go in one `readingOrder` (`places.ts`: page, line band, x).
- **Targets** (`PdfTarget.vue`, `button.pdf-target#place-<encodeURIComponent(id)>`, a dashed accent box labelled `placeLabel`, e.g. "Signature · Mieter, page 2"): found places and unsigned `/Sig` fields; a target a stamp fills gives way to the stamp. Enter, Space or a click is `fillPlace` (`fillOf`): the signature or initials (made first through `openSignatureDialog`) `fitMark`ed into it (shape kept, centred, standing on a found line, in a field's middle; its natural size is the fitted one), a date or place (a place-and-date line: "‹place›, ‹date›", as a place stamp) `fitLines`d at its left on the line; attached (`stamp.place`), selected and focused; `placeRefusal` holds (as the tools' for a stamp), and a target it refuses is `aria-disabled` with the reason as its tooltip. Delete or Backspace on a found place is `dismissShownPlace` ("Place dismissed", one step of the history, no longer in Next); fields can't be dismissed.
- **Fields** (`PdfField.vue`, `pdfFieldModel.ts`): a text field is an input (a textarea when multiline) over the widget, transparent until it has the focus (`.editing`), so the bitmap shows MuPDF's appearance; on focus it takes the field's value, else `prefillText(prefillOf(field))` (the user's name, today's date, `signingPlace`, or both), selected, which only Enter or typing fills in (Tab passing through leaves the field as it was); `maxLen` is its `maxlength`; Enter (Mod-Enter in a multiline one), Tab or blur commit (`commitFill`), Esc drops what was typed. Its keys stay in it (`fieldKeyStays`: all but Tab, Alt and Ctrl/Cmd keys other than select all, copy, cut, paste, undo, redo), so Save's key still signs. A checkbox is `role="checkbox"` (toggles), a radio group `role="radiogroup"` of `role="radio"` buttons on its widgets (`radioBoxes`, each choosing its `onValue`), a combo or list box a `MenuButton class="select pdf-choice"` of its options. A field `placeRefusal` refuses (`PdfView.vue` hands each its `refusal`) is `aria-disabled` with the reason as its tooltip, an input `readonly`, and typing or pressing it says why.
- **Fills** (`fills.ts`): one after another per tab (a queue: each works on the set the one before left, and a value the field holds already is no step, e.g. Enter then blur); `commitFill` asks `fieldRefusal` first, then sends the whole set with the new value (`setFills`); held, it's one step of the book (`changeSheet`) and the pages it returns draw again (`pageRevisions`, `<tab>:<page>` → a count that's part of the bitmap's key, `pageKey(slot, scale, revision)`, so the old bitmap shows stretched meanwhile); refused `missingGlyphs` ("This field's font can't show some of these characters") or `badRequest` it sets `fieldProblem`, shown under the field (`.pdf-field-problem`, the input `aria-invalid`), and the last set stays; another failure says "Blank couldn't fill in this field". `syncFills` (a watcher in `PdfView.vue` on the tab, its opened PDF and `stampBooks`) sends the book's set whenever it isn't the one the helper holds (`sent`, by tab and opened PDF): after undo or redo, once restored, and to a helper opened afresh (Open again: a new `opened`); what the helper holds is recorded once it took it, and a set it didn't take is said (`FORM_FAILED`) and sent again with the next change. `forgetFills` drops a closed tab's, its page revisions too.
- **Next** (`pdf.next`, bindable, no default key, `nextShownPlace`; the toolbar's `.signing-next`, "Next · i of n", "All places filled" and `aria-disabled`): `goNext` focuses the next unfilled place after `lastPlace`, scrolls it to the middle (`scrollIntoView`) and announces `nextMessage` ("Signature on page 3. Press Enter to fill it in.", "… Type to fill it in." for a text field).

## Signatures (`src-tauri/src/signing/trust.rs`, `src/ui/Signature*.vue`)

- `verify.rs` checks each signature (see `signing.md`); `Coverage` says how much of the file it covers. A timestamp token that can't be read leaves `timestamp_unreadable` set and isn't a failing check; one that doesn't hold is. `timestamp_authority` is the certificate in the token: Blank checks that the token holds, not who made it. `weak` names SHA-1 when the digest, the signature algorithm or the SubFilter relies on it. The form's fields come from `form_fields` (`signing/pdf/mod.rs`, which signing uses too): each field once (a set of the ids seen), capped in visits, depth, kids per field and the full name's length, and the pages' widgets are looked at once per page, capped too, so a hostile form can't loop or run out of memory. The check still runs in Blank's own process (lopdf reads the whole PDF there); moving it into the helper, or a process of its own, is the next step if lopdf itself turns out to be attackable.
- `trust.rs`: `classify` → `own` (the user's `certificate.cer`), `trusted` (`signing/trusted/<FINGERPRINT>.cer`, written by `signing_trust` after the user confirmed the fingerprint, removed by `signing_untrust`), `issuedBy` (not self-signed: Blank checks neither certificate authorities nor revocation), `unknown`; `status` → `valid` (whole file, or only validation data later), `signedAgainLater`, `changedAfterSigning`, `invalid`; `checked_all` makes the `CheckedSignature`s the webview shows (the time from the timestamp, else `/M`, in ISO 8601, without an offset when `/M` has none; the timestamp's authority by name, `timestampTrusted` only when its certificate is the user's or one they trust; `weak`; for `signedAgainLater`, `laterSigner`, who signed next).
- The webview: `signaturesModel.ts` says it in words: own and trusted are "Valid", the others only "Intact · says it's issued by …" (the issuer is only what the certificate claims) or "Intact · signer unknown"; the status bar's item (`SignaturesStatus.vue`, command `view.signatures`, no key) sums them up ("Not signed", "Signed", "Signed by 2", "Signed, signer unknown", "Changed and signed again", "Weak signature", "Changed after signing", "Signature invalid", and "Signatures not checked" when the check failed, with ": the file changed" or ": the file is gone" when `pdf_verify` says `fileChanged`/`fileMissing` (`SignaturesUnchecked`; the popover then offers Open again for a changed file); nothing while it runs, and `showSignatures` then only announces it; a result that isn't "ok" is announced, quietly, once it's in). A signature signed again later is never "unchanged": it's "Valid (or Intact) for the version it signed; changed and signed again later by ‹laterSigner›"; a weak one is "Weak: SHA-1 can be forged"; a timestamp is "timestamped by ‹authority› (not checked)" unless trusted; `SignaturesPopover.vue` (request `signaturesPopover`) lists them, `SignatureDetailsDialog.vue` (request `signatureDetails`) shows one, with "Blank doesn't check certificate authorities or revocation." only in its note, and **Trust this certificate…** asks with the fingerprint (`confirmTrust`, `src/signing/trusted.ts`). Settings ▸ Signing ▸ Trusted certificates is `TrustedRows.vue`.
